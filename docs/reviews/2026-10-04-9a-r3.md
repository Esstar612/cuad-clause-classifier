### Draw loop analysis
Termination: each outer pass either advances at least one cursor (finite) or advances none. A no-advance pass means every type is either filled (`accepted == alloc`) or exhausted; exhausted types get `capacity = accepted`, so after `allocate` their allocation is at most `accepted`. `allocate` is a cyclic round-robin over the remainder order (the `open_[1:] + open_[:1]` rotation is a true cycle, and capped types leave permanently). When capacities only decrease and the slot total is fixed, every still-open type keeps at least its previous count, an exhausted type that filled keeps exactly its count, and an exhausted short type gets exactly `accepted`. So no type is ever over-drawn, a no-advance pass with the same allocation can only happen when `len(picked) == 30`, and the loop returns or `allocate` raises. Per-type counts via `sum(p["type"] == t for p in picked)` are correct; the capacity update on `cursor == len(pool)` is right both for short types and types that filled on their last candidate (the re-allocation then returns the same allocation). Pool shuffle is order-independent because of the `(accession, file_name)` sort before the permutation. No bug beyond finding 1.
