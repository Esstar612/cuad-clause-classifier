## Issues, ranked by severity

1. **(Validity, cost) The gate assumes v4 costs the same as v3 on the input side.**
   - The dense schema has 330 required properties per call against v3's 10 arrays. On Claude it sits in the cached prefix (3w). On Gemini the response schema may be billed as prompt tokens.
   - This is measurable now. The v3 smoke used the same three windows (c15_w0 to w2, BUILD_LOG 3z), so the gate can take the per-call input difference between v4 and v3 on identical call keys:
     - Gemini: `prompt_token_count` difference at `price_in`.
     - Claude: prefix token difference (cache_creation + cache_read) at the cache-read price, plus any `input_tokens` difference at `price_in`.
   - Also, the formula as written omits `/1e6`. `price_out` is per million tokens (config.py:72-76).

2. **(LLM behavior) A timeout can pass the 90 s check.**
   - `latency_ms` covers only the successful round trip (clients.py:28), and timeouts are retried.
   - So a smoke call that hit the 120 s timeout and then succeeded on retry would look fine.
   - The gate should:
     - treat any timeout in a smoke attempt's `retry_errors` as breaching 90 s;
     - print `transport_retries`;
     - require all 3 smoke records per model. If any are missing, the stop condition is not met.

3. **(Claim, validity) The N=1 count is an approximation.** 1,677 is half the segments. The gate should use either an upper bound (segments in the 12 largest iteration contracts) or the seeded draw, and label which it used. The gate result sits close to $100, so this matters.

4. **(Pre-registration) Rule E has no branch for "Claude fits, Gemini does not".**
   - The three branches do not say what happens if Gemini rejects the dense schema or fails the stop condition while Claude passes.
   - The amendment should also say how a single model failing the stop condition maps to a branch.
   - This must be written before the smoke. It needs your decision (below).

5. **(Correctness) The `heldout` dense branch can crash.** run.py:967, 972-973 read `status` and `health['below_floor_share']`. The dense branch has to set its own status and notes. Any crash would come after the calls are paid for; they are cached, so a rerun resumes without paying again. The test should run through the notes, not just check that `record_health` is skipped.

6. **(Consistency) The yardstick rerun has no command.** A rerun that writes to `llm_yardstick.txt` would change a file 3aa cites. Give the command, with a new output file.

7. **(CLAUDE.md, honesty) Two verification gaps.**
   - Verification says v1 to v3 rebuild unchanged, but no commands are given.
   - The pinned v1 to v3 `prompt_hash` values must come from existing output, such as the `model_version` column in the iteration parquets, not be typed from memory.

8. **(Missing tests)**
   - `scores_note` for each version.
   - `_raw_entries` raises for a dense version.
   - `gate-v4`: the input difference, a timeout in `retry_errors`, and an incomplete smoke.

**Optional notes, not required:**

- "Degenerate" as defined also counts legitimate all-zero windows. Consider reporting the identical-nonzero share separately.
- The `macro_ap_sparse_lower_bound` name (from r1) still needs a note in the write-up.

No leakage: retrieval is train-only and iteration uses only validation contracts. The v4 edits don't change what any category means, so there is no label or legal question. No em dashes or attribution problems. Commands are given, not run.
