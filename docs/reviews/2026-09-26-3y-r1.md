**1. Correctness bug in proposed test 4 (medium).**

- Fix: the test must name its spec. Either use `config.LLM_MODELS["claude"]` (cache read) or the stub spec (system at `price_in`), and write the expected value to match. Output tokens cancel out because the targets are the same.
- The plan should also say where the "validation call" comes from. `_segments()` produces the synthetic text "text 7-3", which gives the retrieval nothing meaningful to match. A real validation window from `load_segments()` is better, and it needs `@needs_baseline`.

**2. Test 3 can pass for the wrong reason (medium).**
- "Projects more than $0" is also true when no record was saved at all.
- The test should first assert that the cached record exists with `retry_pending` True. It should then check that the projection equals that call's ledger rate, and that it drops to 0.0 after a successful resume.

**3. Fix 1 has no test (medium).**
- Missing test: run the call until a `retry_pending` record exists, then rewrite the stored attempt's `text` to valid JSON while leaving the stale `parse_errors` in place. On resume with `StubClassifier([])`, the stub sends 0 requests and the saved record has `retry_pending` False.
- With this test the expected count becomes 114, not 113.
- Also note: in this path `_run_one` returns `new=True` even though nothing was sent, so `new_calls` overcounts by one. This is cosmetic; the test should assert on `sent`.

**4. Budget flag for the full v3 runs is not stated (low).**
- Step 3w projects Claude v3 iteration at $4.76. The last Claude iterate command used `--max-cost 4` (line 1635). Reusing it would stop the run partway, splitting its run window.
- The plan should give the full commands with explicit `--max-cost` values above the projections.

**5. The smoke check for "examples reached the request" has no stated method (low).**
- Cache records do not store the user message. The plan should give a concrete check, for example v3 `input_tokens` against v2 on the same `--limit 3` calls.
